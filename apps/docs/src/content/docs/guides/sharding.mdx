Shardlens works with every common sharding setup without extra configuration. Create one Shardlens instance per
discord.js `Client`, in the process where that client runs.

| Setup                   | Where `createShardlens` goes                     | How events are tagged                         |
| ----------------------- | ------------------------------------------------ | --------------------------------------------- |
| Internal sharding       | Your bot file, once                              | Each event carries its guild's shard          |
| `ShardingManager`       | The shard file (not the manager), once per shard | The shards that process runs                  |
| discord-hybrid-sharding | The cluster file, once per cluster               | The cluster's shard list                      |
| Several machines        | Each process                                     | `source.instance` tells hosts apart           |

## Stopping a sharded bot

Each shard or cluster process flushes its own events, so each needs the
[shutdown handler](../../getting-started/configuration/#shutting-down) for both `SIGINT` and `SIGTERM`. Ctrl+C in a
terminal reaches every process, but a signal sent to the manager alone (`docker stop`, systemd, a hosting platform's
restart) does not: the shards keep running, and are killed without flushing once the manager exits. Pass the signal on

## What happens across shards

- **Totals** (servers, members) add up the latest value from every shard. A shard that hasn't reported for 2 minutes
  is shown as stale, not as zero.
- **App-wide work** (application info, the registered command list, the gateway session budget) runs only in the
  process that owns shard 0, so it isn't repeated per shard.
- **No `broadcastEval`**: Shardlens never sends code between shards.
- **Guild snapshots** at startup are taken per shard, so joins and removals while the bot was offline are found on
  every shard.

<Aside type="note">
  With a collector on a server, use the same ingest key in every process. The collector tells processes apart by host
  and shard.
</Aside>

## On your bot's MongoDB

With [`mongodb`](../../self-hosting/mongodb/), each process runs a collector of its own against the same database:

- **Placement** is as above: once per process, in the shard or cluster file.
- **Keys** are generated once, by whichever process starts first, and shared by all of them through the database.
- **Background jobs** (rollups, unique users, retention, alerts, reports) run in one process at a time, on a lease in
  MongoDB renewed three times a minute. If that process stops, another takes over within about a minute and a half.
- **Connections:** each process opens at most 5 to MongoDB (10 while it serves the dashboard), beside the bot's own.
- **The dashboard**, if the bot serves it with `mongodb: { uri, dashboard: { port } }`, is served by the first process
  to take the port; the others leave it alone. `npx shardlens dashboard` needs none of this.
