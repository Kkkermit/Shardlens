Already have a web dashboard for your bot? You don't have to send people to a second one. Everything the Shardlens
dashboard shows comes from one endpoint, `POST /v1/query`, and your own backend can call it with a **read key**. The
collector keeps doing the collecting, storing and counting; you decide how it looks.

## 1. Create a read key

In the Shardlens dashboard, **Settings → API keys → Create**, scope **read**. It is shown once. A read key can run
queries and nothing else: it can't send events, change settings or see who ran a command.

Put it in your dashboard's server environment as `SHARDLENS_READ_KEY`, next to `SHARDLENS_URL`.

<Aside type="caution" title="Server side only">
  Call the collector from your backend, never from browser code: anything in a page can be read by whoever opens it.
  The collector sends no CORS headers for the same reason.
</Aside>

## What you can ask for

Every query is a JSON object with a `kind`. Ranges are ISO timestamps, at most 400 days apart.

| `kind`                              | What comes back                                                                                          |
| ----------------------------------- | -------------------------------------------------------------------------------------------------------- |
| `overview`                          | The app, runs and failures per day for the last 30 days, the server count, unique users this period, and the state of each bot process's SDK |
| `commands`                          | Every command: runs, change on the previous period, failure rate, p95, servers, unique users             |
| `command`                           | One command in depth: subcommands, options, channel types, member tiers, languages, top servers, latency |
| `series`                            | A metric over time (`interval`: minute, hour, day, week or month), optionally split with `groupBy`       |
| `top`                               | The top values of one dimension: commands, servers, languages, outcomes                                  |
| `heatmap`                           | Hour-by-weekday counts in your time zone                                                                 |
| `servers`, `server`                 | The server list (search, sort, page) and one server's profile                                            |
| `growth`, `audience`                | Joins and leaves, retention cohorts, daily and weekly unique users                                       |
| `reliability`                       | Response-time percentiles, missed deadlines, errors by Discord code, REST health, shards, memory         |
| `gauge`                             | One gauge over time: `shard.ping_ms`, `shard.guilds`, `memory.rss_bytes`, `eventloop.p99_ms` and the others in the [metrics list](../../concepts/metrics/). `perShard: true` gives a line per shard |
| `bursts`                            | Minutes in the last 14 days with several times the usual number of interactions                          |
| `premium`, `installs`               | Entitlements by SKU, user installs                                                                       |
| `events`, `eventProps`              | Your custom events and their properties                                                                  |
| `funnel`, `retention`               | Conversion through steps, and cohort retention                                                           |

`series` and `top` take `filters`, so one server's numbers are a filter on `guild` away, as in `topCommandsIn` above.
The full schema of every query is in the [HTTP API reference](../../reference/http-api/) and at `/openapi.json` on
your collector.

There is no `groupBy: 'user'` and no per-user query: that is by design, in every mode.

## What you can split a metric by

`groupBy` and `filters` take the dimensions the metric keeps. Asking for another one is answered with `400` and
`{ "error": "invalid_query" }`, with a `message` that lists the ones you can use.

| `metric`                                    | Dimensions                                                              |
| ------------------------------------------- | ----------------------------------------------------------------------- |
| `interactions`                              | `kind`, `command`, `sub`, `outcome`, `context`, `install`, `locale`, `tier` |
| `interactions`, with `guild` in it anywhere | `guild`, `kind`, `command`, `outcome`                                   |
| `components`                                | `kind`, `custom_id`, `source`, `outcome`, `guild`                       |
| `interactions.autocomplete`                 | `command`, `option`                                                     |
| `modals.shown`, `modals.submitted`          | `command` and `custom_id`; `custom_id` and `outcome`                    |
| `interactions.errors`                       | `command`, `error_class`                                                |
| `rest.calls`, `rest.invalid`, `rest.ratelimits` | `method`, `route`, `status`; `status`; `scope`, `route`             |
| `guild.joins`, `guild.leaves`, `guild.unavailable` | `detected`                                                       |
| `custom` (with `name`)                      | None: use `eventProps` for an event's properties                        |

Per-server numbers are kept for fewer dimensions on purpose, so the store doesn't grow with commands × servers ×
everything else.

## Reading the answers

- **Times in a series** look like `2026-11-12T14:00:00`: the start of the bucket in the `timezone` you asked for
  (UTC if you didn't), with no offset. An hour or day in which nothing happened is left out, not sent as zero.
- **Intervals have limits.** `minute` series cover at most 2 days and only the last 14; `hour` series at most 31 days.
- **Ranges are read in whole hours.** A range that starts at 15:20 is read from 15:00, so "the last hour" always has
  something in it. Ranges that start more than 13 months back are read in whole days.
- **Unique users** are recounted every 5 minutes, per UTC day, and "this period" is the current salt period (a month
  by default). Everything else is at most a minute behind.
- **Percentiles** (`p50`, `p95`, `p99`) come from a histogram with fixed buckets, so they read as the upper edge of
  the bucket they fall in: up to a third above the true value, never below it.
- **Missed deadlines** count both a reply Discord refused as too late and an interaction that got no reply at all.
- **HTTP-interaction bots** (`@shardlens/http`) have no gateway, so `servers`, `growth`, shard and REST numbers stay
  empty for them. Interactions, audience and custom events work the same.

## Good manners

- **Cache.** Numbers are rolled up once a minute, so caching a response for 60 seconds loses nothing.
- **Limits.** `/v1/query` allows 600 requests a minute per address and answers `429` with `Retry-After` past that.
- **Rotate** the key from **Settings → API keys** if it ever leaks: create a new one, deploy it, revoke the old one.

## Other ways to get the numbers out

- **Into Discord:** a [scheduled report](../reports/) posts a daily or weekly summary to a channel, and
  [alerts](../alerts/) tell you when something breaks.
- **Into Grafana:** the [Prometheus and OpenTelemetry exporters](../grafana/) send bot-health metrics to the
  monitoring you already run, with or without a collector.
- **Live:** `GET /v1/live` is a Server-Sent Events stream of interactions per minute, p95 and shard state.
